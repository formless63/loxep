title: Fleet Observability Design (Phase 8)
---

This document designs Phase 8 — the **observe and link** layer of the `/infrastructure` workspace. [Infrastructure Control Plane Design (Phase 7)](../infrastructure-control-design/) named this layer, deferred it, and drew the line it must stay inside. Phase 8 does not extend that line; it lives entirely underneath it.

**Design work only.** No migration, Drizzle schema, integration package, or service code is authorized by this page. Every upstream fact below was verified against current sources on 2026-08-13 and must be **re-verified immediately before implementation** per the [dependency policy](../../development/dependency-policy/) — three of the six candidate tools shipped a release within the last ninety days, and one of them is eight months old.

Phase 8 depends on the foundation and, for its user-facing surfaces only, on Phase 7 milestones. Its first milestone depends on neither.

**Implementation status — milestones 1 and 2 are IMPLEMENTED (loxep-ovj.1, loxep-ovj.2).** Milestones 3 and 7 remain design only. What shipped, and how each "Before implementing this phase" item and open question was resolved for milestone 1:

- **Migration `0014_integration_health`** creates the one table exactly as designed — `integration_health`, primary key `(subject_type, subject_id)`, no surrogate key, no foreign key on `subject_id`, all four `CHECK`s (subject_type, status, source, and the `(status = 'ok') = (consecutive_failures = 0)` biconditional) generated by drizzle-kit without hand-writing. No existing table gained a column, and nothing was dropped from `connections`' or `monitor_targets`' own error/backoff columns.
- **Open question 6, resolved per its own recommendation:** `integration_health` ships as shared foundation in `@loxep/domain` (`health.ts`'s `createHealthService` — `upsertHealth`/`getHealth`/`listHealth`/`clearHealthForSubject` — and `health-probes.ts`'s subject registry and sweep), not in `@loxep/infrastructure`. `hosting_target` and `managed_domain` are in the migration's `CHECK` from day one, per the recommendation, but have no registry entry yet — Phase 7 wires a projection into them when it lands, and nothing here assumes it has.
- **"Before implementing" item 5 (idempotency tests)** and item 6 (only `GET` may leave the boundary) are both covered: `packages/domain/test/health-probes.test.ts` proves two probes of the same subject upsert in place, a subject deleted between listing and probing clears its row instead of writing a stale one, and an unreachable subject renders `'unknown'` — never `'failing'` — distinctly from a subject that responded and failed. Every default probe (`health-default-probes.test.ts`) sends only `GET`/`HEAD`-shaped read calls; none sends a credential, a token, or an `Authorization` header, checked directly in the ntfy probe's test.
- **Item 8 (no credential/response body in `detail`)** is enforced by the service, not left to per-adapter review: `upsertHealth` throws `DomainValidationError` outright — never silently redacts — when `detail` carries a sensitive-shaped key (the same scan `@loxep/domain`'s audit redaction uses) or a raw-payload-shaped key (`body`, `headers`, `response`, `html`), tested in `health.test.ts`.
- **First subjects, exactly as scoped:** `connection` (derived from `connections.last_success_at`/`last_error_at` — no network call), `notification_endpoint` (ntfy's unauthenticated `GET /v1/health`), `storage_backend` (`local`: `fs.stat` on `rootDir`, same host as Loxep so a failure is `'failing'`, not `'unknown'`; `s3`: an unauthenticated `HEAD` to the configured endpoint — any HTTP response, even a 403, proves reachability). No companion-tool probe shipped, per scope.
- **The sweep is `health.sweep`, ONE recurring Graphile Worker job, every 5 minutes, no `monitor_targets` row** — resolving the tension the design names against [Phase 7's open question 5](../infrastructure-control-design/#open-questions) by taking the "no" branch this page recommended. Due-ness is `checked_at + interval(consecutive_failures)`, computed in `@loxep/domain`'s `nextHealthCheckDueAt` (base 300s, doubling per consecutive failure, capped at 3600s) — no new column, exactly as designed. Work is bounded per subject type per run (`DEFAULT_MAX_SUBJECTS_PER_TYPE = 50`), mirroring `commerce.redact-order-payloads`' batch shape. The sweep MECHANICS live in `@loxep/domain` as a plain async function with no `@loxep/jobs` dependency (`runHealthSweep`); `packages/app/src/health-sweep.ts` is only the `defineTask` + cron wrapper, the same division `ebay.refresh-tokens` already uses for a task `@loxep/app` owns outright.
- **Tested, per the design's load-bearing rule:** `integration_health` never drives retry or backoff. `packages/domain/test/health-probes.test.ts` inserts a `connections` row with `last_error_at`/`last_error_code` set and a `monitor_targets` row with `backoff_until`/`consecutive_errors` set, runs the sweep, and asserts both rows are byte-for-byte unchanged afterward while `integration_health` reflects the probed status.
- **Where this surfaces, this milestone:** the `/dashboard/overview` Operations band's `ConnectionsCard` now reads its per-provider "erroring" count from `integration_health` (`subject_type = 'connection'`) instead of re-deriving it from `connections.last_error_at`/`last_success_at` in-process — the one place this milestone's subjects overlap what the band already showed. Everything else on the band (the monitor fleet, order-sync freshness, notification delivery rate) is unchanged and stays derived, because none of it is a probed subject type yet. `/settings/overview` gains an "Integration health" table (`IntegrationHealthReport`, the donor `DataTable` stack) listing every subject by status, source, and last-checked time, labeled from its owning table (`connections`/`notification_endpoints`/`storage_backends`). `/infrastructure`'s fleet-health summary and the per-tool "Tools" panel remain future work — Phase 8 milestone 1 has no fleet subjects yet.
- **Not built in this milestone, on purpose:** the Gatus outward push (milestone 9's recommendation, still open at the time) and evidence ingestion / the inbound webhook (open question 4, deferred). The push shipped next, as milestone 2, below. Evidence ingestion shipped much later, as milestone 7 (loxep-ovj.7) — see that milestone's own implementation-status paragraph near [Evidence ingestion, if it ships](#evidence-ingestion-if-it-ships).

**Implementation status — milestone 2, the Gatus outward push, is IMPLEMENTED (loxep-ovj.2).** Open question 9's recommendation ("yes, and first") was taken. What shipped, and the one open question it left explicitly unresolved:

- **Config split, following every other provider base-URL/credential pair in this codebase:** a new registered setting, `infrastructure.gatus_push` (`@loxep/domain`'s `gatusPushSetting`) — `enabled`, `baseUrl`, and `endpointKey`, the non-secret half an operator types to point Loxep at an endpoint that already exists in their own gatus YAML. The bearer token Gatus's `external-endpoints` entry requires is the secret half: it is stored as the application secret `infrastructure.gatus_push.default` (purpose `token`, the same generic bundle `notification_endpoints` already uses for its own bearer tokens), never in the setting's JSON and never in a Compose env var. Both `@loxep/app` (which reads it) and `apps/web` (which writes it) import the same `GATUS_PUSH_SECRET_KEY` constant from `@loxep/domain` rather than each hard-coding the literal, so the two sides of the split cannot drift apart. `enabled` defaults to `false` and the URL/key default to `null` — the same "nothing configured must not look like ready" discipline `caaPolicySetting` uses.
- **What gets synthesized, resolving open question 9's "which facts" half PROVISIONALLY:** rather than the five candidate facts the open question named (worker backlog, order-sync freshness, notification delivery success, reconciler drift count, readiness), milestone 2 ships ONE signal — Loxep's overall `integration_health` status, the worst of every subject row (`failing` beats `degraded` beats `unknown` beats `ok`), reported as Gatus's binary `success`/`error`. This is a deliberate, narrower reading of the open question, not the owner's final word on it: it is the cheapest thing that is honestly "Loxep's own readiness" without inventing a rollup across four unrelated subsystems that have no shared severity model yet. Widening the published fact set (or splitting it into several endpoints) remains open — see the amended open question below.
- **`duration` is diagnostic, not a health signal:** it reports the wall-clock time the push spent computing the `integration_health` summary, not a round-trip time to some other service. The push's own act of completing at all is the liveness signal the operator's `heartbeat.interval` depends on — if the Loxep process is down, no push happens, and that silence is exactly what Gatus's heartbeat is for.
- **Five-kind outcome, and the push never throws a job down:** `@loxep/app`'s `pushGatusHealth` (`packages/app/src/gatus-push.ts`) returns `disabled` / `unconfigured` / `network_error` / `http_error` / `ok` rather than throwing for any reachable failure. A failed push is Loxep's own reporting problem, not a reason to fail the cron run loudly; anything other than `ok`/`disabled` is logged as a structured warning by the task wrapper. There is deliberately no `integration_health` row for this outcome — every row in that table describes one of the schema's own closed `subject_type` values, and "Loxep's push to Gatus" is not one of them; a structured log line is the honest record instead of misusing an unrelated subject type.
- **Schedule: piggybacked on `health.sweep`'s own cadence**, per the design's own recommendation against a second operator-tunable interval — `infrastructure.gatus-push` is a second `*/5 * * * *` Graphile Worker cron task (`createGatusPushTasks` in `gatus-push.ts`), registered in `registry.ts` alongside `health.sweep`, not a `monitor_targets` row.
- **The route/key format/query parameters were re-verified against Gatus's own README on 2026-08-13 (v5.36.0 current):** `POST /api/v1/endpoints/:key/external?success=&error=&duration=` with `Authorization: Bearer <token>`, and the key is `<sanitized group>_<sanitized name>` — Gatus itself replaces ` `, `/`, `_`, `,`, `.`, `#`, `+`, and `&` in the group and endpoint name with `-` before joining the two halves with a literal `_`. The [operator guide](../../guides/gatus-health-push/) states that sanitization rule explicitly, because a mismatched key is a silent no-op rather than an error.
- **Where this surfaces:** a "Gatus outward health push" card on `/settings/application` (`GatusPushCard`, following `NotificationEndpointDialog`'s write-only token pattern exactly — the token field always renders blank and a save with it empty leaves the stored token untouched). No `/infrastructure` surface yet, matching the rest of this phase.
- **Tested:** `packages/app/test/gatus-push.test.ts` covers the push's exact URL/method/`Authorization` header shape, the worst-status synthesis, all five outcome kinds (including a genuinely unreachable base URL and a non-2xx Gatus response, both via an injected fetch — no real network I/O), and that the task/cron wrapper never throws. `packages/domain/test/settings.test.ts` covers the setting's schema (including rejecting a malformed endpoint key) and the shared secret-key constant.
- **Amends open question 9:** *"which facts should be published"* is answered PROVISIONALLY as "overall `integration_health` status, alone" rather than the five-fact list the question named — narrower than what was asked, and recorded as such rather than silently substituted. **The owner must confirm** whether the narrower signal is sufficient or whether worker backlog / order-sync freshness / notification delivery success / reconciler drift count should each become additional Gatus endpoints (Gatus's `external-endpoints` model supports declaring several).

**Implementation status — the OQ9 five-fact expansion is IMPLEMENTED (loxep-4ah, owner ruling 6b, 2026-08-15).** The owner confirmation open question 9 asked for arrived, and answered it "yes, widen it" — resolving open question 9 for good rather than leaving it open:

- **Additive setting field, PROVISIONAL default unchanged:** `gatusPushSetting` gains `mode: 'single' | 'facts'` (`@loxep/domain`, schema version unchanged — the field carries its own Zod `.default('single')`, so a value stored before it existed still parses and behaves exactly as milestone 2 shipped). `mode: 'single'` is the default and is **byte-for-byte unchanged**: `pushGatusHealth` is untouched, its own test suite passes without modification, and one push still goes to `endpointKey` itself.
- **`mode: 'facts'` publishes the five candidate facts milestone 2 narrowed away from**, each to its OWN derived Gatus key (`@loxep/domain`'s `deriveGatusPushFactKey(endpointKey, slug)` — `<endpointKey>-<slug>`, never `endpointKey` itself): `worker-backlog` (`@loxep/jobs`' `getJobStats` against `graphile_worker.jobs` — failed jobs or an oldest-pending job over 15 minutes fails the fact), `sync-freshness` (the worst `integration_health` connection status among ebay/woocommerce/etsy/reverb/medusa — the SAME rollup `/settings/overview` already shows), `notifications` (`notification_deliveries.status = 'failed'` in the last 24h), `drift` (`managed_domains.drift_detected_at IS NOT NULL` plus every connection's persisted `detail.driftingTargetCount` — both already-computed signals, never a second reconcile pass), and `readiness` (narrowed to database reachability — `@loxep/app` cannot depend on `@loxep/runtime`'s fuller readiness report without a new package dependency edge, out of this bead's scope; recorded so a later session can widen it). A fact whose computation throws is SKIPPED that cycle, never reported as a fabricated failure.
- **The operator must declare FIVE `external-endpoints` entries**, one per fact, whose sanitized Gatus keys match the five derived keys — see the updated [Publishing health to Gatus guide](../../guides/gatus-health-push/) for the exact YAML block.
- **The feedback-latch quarantine (BINDING RULE 1) extends to all five derived keys in `mode: 'facts'`**, via one shared helper (`fleet-health.ts`'s `gatusPushQuarantinedKeys`) both the read-side heartbeat mirror and the discovery exclusion now call — the two can no longer quarantine a different key set from each other, or from what `gatus-push.ts` actually pushes to. The base `endpointKey` itself is NOT quarantined in `facts` mode (it is a derivation seed only, never pushed to directly, so it is free to be an ordinary Gatus endpoint the operator tracks independently). The heartbeat mirror mirrors from the bulk `statuses` page only in `facts` mode — it does not issue up to five extra unauthenticated GETs per sweep the way `single` mode's one fallback GET does for its one key.
- **Tested:** `packages/app/test/gatus-push.test.ts`'s `pushGatusHealthFacts` suite covers the fan-out on `disabled`/`unconfigured`, the derived-key POST shape, a skipped fact (no `graphile_worker` schema), and two facts (`sync-freshness`, `drift`) reading real persisted state. `packages/app/test/fleet-health.test.ts`'s BINDING RULE 1 quarantine suite gained a `mode: 'facts'` case asserting all five derived keys are excluded from discovery while the base seed and an unrelated sibling endpoint stay linkable. `packages/domain/test/settings.test.ts` covers the additive field's backward compatibility and the key-derivation helper.
- **This resolves open question 9 completely** — both halves ("yes, and first" and "which facts") now have an owner ruling behind them.

**Implementation status — the Gatus READ adapter is IMPLEMENTED (loxep-ovj.4).** gatus.io/docs renders client-side and returns an empty body to a fetcher, so every fact below — the exact route table, the auth branch, and the response shapes — is re-verified directly against `github.com/TwiN/gatus`'s own Go source at tag `v5.36.0`, not the docs site this page's earlier verdict relied on. The verdict itself does not change: this confirms it rather than amending it.

- **The auth branch, confirmed structurally rather than inferred:** `api/api.go`'s `createRouter` only ever calls `cfg.Security.ApplySecurityMiddleware` `if cfg.Security != nil` — so "the API is fully open when no `security` block is configured" is not an inference from behavior, it is the one `if` that gates the only place auth middleware is attached. `GET /api/v1/config` (`api/config.go`) is unauthenticated and answers `{oidc, authenticated}`; `security/oidc.go` confirms OIDC's only session-issuing route is `POST /authorization-code/callback` after a browser redirect, storing a session id in an in-memory cache (`security/sessions.go`) and returning it as an `HttpOnly` cookie — no bearer path exists for a server-to-server reader to hold. The adapter probes `/api/v1/config` before every attempt at the protected bulk read and refuses outright, with zero network calls, when `oidc: true`; it falls back to the two unprotected per-endpoint routes (`GET .../uptimes/:duration`, `GET .../response-times/:duration`), which sit above the `if cfg.Security != nil` branch entirely and so need no credential in any security mode.
- **The one write path in Gatus's whole route table stays exactly what milestone 2 already used it for**: `POST /api/v1/endpoints/:key/external`, gated on its own bearer token, reserved for the outward push. This read adapter exports no function that could reach it — every read is a `GET`, with no login-exchange exception the way Beszel's adapter needs one (Gatus's Basic auth carries the credential in a header on every request; there is nothing to exchange).
- **What shipped:** `@loxep/integration-gatus` (read-only; `test/boundary.test.ts` asserts every recorded request is a `GET`, that Basic auth is attached to the protected bulk-statuses route only, and that no credential reaches a URL or an error detail), the `gatus_credentials` bundle in `@loxep/domain` — the one credential bundle in this registry whose two fields are OPTIONAL together, because an open or OIDC-secured Gatus legitimately has nothing to store — and a new `integration.gatus.rate_budget` setting mirroring `integration.cloudflare.rate_budget`'s shape (Gatus documents no rate limit of its own). Catalog/guided-form wiring in `apps/web` (`/settings/connections`, Infrastructure category) follows the Tailscale/Termix pattern, with its own copy explaining the three security modes rather than asking the operator to guess which one applies — **with no migration**, `connections.provider`/`connections.kind` being ordinary text columns.
- **Not built in this milestone:** `packages/app` executor/task routing and the `integration_health` projection this adapter's reads would feed (follow-up, matching every other milestone in this phase that shipped an adapter before its fleet-panel wiring), and the `/api/v1/suites/statuses` routes the per-tool verdict table below also names — this milestone covers `endpoints` only, matching the auth-branch design's own scope.

**Implementation status — the connection-level probe closed by `loxep-rf4`/`loxep-1au` (2026-08-13).** The fleet-aware `connection` registry (`fleet-health.ts`) now probes Gatus with exactly the three-posture logic this section's route table specifies: `probeConfig()` first, then `listEndpointStatuses()` in `open`/`basic` posture (the credential-proving, discovery-yielding, endpoint-counting read) or `health()` in `oidc` posture (`degraded`, never `failing`, for the reason this section already gives). ## The line this phase inherits

Phase 7's ownership statement is binding here, and Phase 8 is almost entirely its third row:

```text
Loxep OWNS          declared intent for names and DNS, and the reconciliation
                    of that intent against the providers that hold it

Loxep OBSERVES      provider state, the diff against intent, and delegation status

Loxep LINKS         container management, host/container metrics, uptime probing,
                    terminal access — through external_resources / resource_links
                    and the integration-health model, never reimplemented

Loxep NEVER OWNS    configuration management, image builds, deployment pipelines,
                    provisioning of servers, or anything that runs ON a host
```

[Domain Boundaries](../domain-boundaries/#infrastructure) states the same rule as a boundary: Infrastructure does not own *"container orchestration, host metrics, or uptime probing… Infrastructure may hold links and health state for them under the generic external-resource and integration-health models, and must not grow into a reimplementation of them."*

Phase 8 adds one falsifiable marker of its own, because the third row is easy to cross by accident:

> **Loxep stores the latest observed status of a subject. It never stores a metric sample.**

If a milestone proposes a hypertable, a chart of CPU over time, a retention policy for host metrics, or a "last 24 hours of response times" table, that milestone has started rebuilding Beszel or Gatus and the [Master Domain Map's non-goal](../../product/master-domain-map/#what-loxep-is-not) wins. One row per subject, overwritten in place, is the shape that makes the rule enforceable by inspection rather than by intent.

The second marker follows from the first:

> **Loxep never calls a mutating endpoint on a fleet tool.**

Dockhand can restart a container and redeploy a stack over HTTP. Beszel can update a system record. Those calls exist and are reachable. An adapter that made one would be doing exactly what the fourth row forbids, regardless of how the UI described it. Adapters designed here are **read-only by construction**, with two deliberate exceptions: the Gatus health push argued below, which writes Loxep's own health outward and touches nothing on any host, and the host-registration carve-out the owner granted on 2026-08-13.

#### AMENDED 2026-08-13 — the host-registration carve-out, stated precisely

The owner ruled that registering and configuring a host in a container manager is **Phase 7-style desired state**, not a forbidden verb: *"adding a new VPS could be pretty simple when it's all here"*. The carve-out is narrow and its boundary is drawn on the **resource**, not the HTTP method:

```text
PERMITTED    the companion's own INVENTORY OF HOSTS — an address, a connection
             type, a TLS bundle, a label. Writing one creates a row in the
             companion's database. Nothing executes on the target machine.

FORBIDDEN    everything that acts on a Docker daemon: start, stop, restart,
             kill, exec, deploy, redeploy, delete, prune, pull, terminal,
             file browse. Code runs ON a host.
```

The review test is therefore **"does this call cause code to run on a managed host?"** — never "is this a POST?", which would have blocked a login exchange and permitted nothing useful. That question separates `PUT /api/environments/{id}` from `POST /api/containers/{id}/start` at exactly the place the fourth row already sits, which is why the carve-out can be granted without moving the line.

Two consequences bind implementation:

- **The carve-out is per resource, not per adapter.** An adapter that gains host registration does not thereby gain lifecycle. `@loxep/integration-dockhand` enforces this in `test/forbidden-verbs.test.ts`, which asserts both the exported surface (no member is named after a lifecycle verb) and the traffic (every request is a `GET` except the login and the two host-registration writes).
- **There is no `delete`.** Removing a host from a companion's inventory is not Loxep's decision; an operator who decommissions a machine says so in `hosting_targets`, and Loxep's response is to stop reconciling it. The operation union is closed at `create | update` so that adding a delete needs an owner ruling rather than a union member.

## The self-monitoring trap, which decides most of this phase

Every other Loxep integration observes something Loxep does not run on. eBay does not stop working because the Loxep container died. The fleet does.

```text
Loxep runs on the fleet it would be observing.

Therefore anything Loxep is in the critical path of cannot report
Loxep's own outage — and the outage of the host Loxep runs on is
the single most important alert in the whole estate.
```

That one observation resolves the largest open design question — whether infrastructure alerts should route through Loxep's notification pipeline — and it resolves it against Loxep. It also inverts the phase's most obvious assumption: the most valuable thing Loxep can do with Gatus is not *read* it, but **be watched by it**.

### What the operator already has

Every candidate tool speaks ntfy natively:

```text
beszel     Shoutrrr, with Ntfy among 25 services      settings -> notifications
gatus      Ntfy alerting provider (topic/url/token/priority)
netdata    SEND_NTFY / DEFAULT_RECIPIENT_NTFY in health_alarm_notify.conf
dockhand   ntfy among ~10 outbound notification channels
```

The operator running Loxep already has ntfy configured, because [ntfy is Loxep's first notification transport](../../development/implementation-contract/#notifications). So a host-down alert from Beszel and a price-drop alert from Loxep already arrive on the same phone, in the same app, from the same server — **and ntfy, not Loxep, is what unified them.** Inserting Loxep as a relay between Beszel and ntfy adds a hop, a failure mode, and a dependency on the very machine being reported on, in exchange for a unification that already exists.

### What the delivery ledger physically is

Independently of that argument, the schema says no. `notification_deliveries` is not domain-neutral today:

```text
notification_deliveries
market_event_id   uuid NOT NULL references market_events(id)
endpoint_id       uuid NOT NULL references notification_endpoints(id)
unique(market_event_id, endpoint_id)
```

and `market_events.marketplace_item_id` is itself `not null` against `marketplace_items`. The `notifications.deliver` job payload is `{ marketEventId, endpointId }`, and the deduplication key — the property that makes at-least-once delivery safe — is that unique pair. There is no seam for a subject that is not a market event about a marketplace item.

The **transport** is genuinely neutral: `NotificationMessage` is `{ title, body, priority?, tags?, url? }` and knows nothing about markets. The **ledger and the rule matcher** are not. Routing an infrastructure alert through the existing pipeline therefore means altering a shipped foundation table to a polymorphic subject, rewriting the dedupe key, and generalizing `notification_rules.market_event_type`. That is a real, defensible piece of work — it is simply not work this phase should do in order to become a slower ntfy.

### The resolution

```text
DETECTION      the companion tool detects (host down, endpoint failing,
               container unhealthy). It is better at this than Loxep and
               it keeps running when Loxep does not.

DELIVERY       the companion tool delivers, directly to ntfy. Loxep is not
               in the path. No change to notification_deliveries.

EVIDENCE       Loxep may additionally receive a copy as an inbound webhook,
               record it, and roll it into health state. Recording is not
               delivering.
```

This is the contract's *"event detection and notification delivery remain separate concepts"* rule read honestly, with Loxep on the consuming side of a detection it did not perform. It is also the only arrangement in which the alert still fires when Loxep is the thing that broke.

**What would falsify it:** if the operator ever wants one Loxep-authored rule that fans an infrastructure alert to several transports, this design is wrong and the ledger must be generalized. That is [an open question](#open-questions), not a settled call.

## Does Loxep run its own uptime probes?

Loxep already owns a scheduler ([`monitor_targets`](../foundational-data-model/#monitoring-model)), durable jobs with backoff, and health conventions ([ADR-0018](../../decisions/0018-runtime-processes-migrations-health/)). Adding an "enter a URL and an interval" form is perhaps a day's work. [Principle 18](../principles/#18-integrate-before-rebuilding-mature-specialist-products) says do not.

The recommendation is **no**, and the line is drawn by *what the subject is*, not by how the check is implemented:

```text
Loxep PROBES        a subject that is already a Loxep record and that Loxep
                    itself depends on — a connection, a notification endpoint,
                    a storage backend, a registered companion tool's own
                    health path. "Can Loxep reach the things Loxep needs?"

Loxep DOES NOT      an arbitrary operator-supplied URL, port, DNS name, TLS
PROBE               expiry, or certificate, on a schedule the operator tunes,
                    with per-check conditions and per-check alerting.
                    That is Gatus, and Gatus is very good at it.
```

The first is **integration health** and Loxep has needed it since Phase 0 — [Companion Services](../../product/companion-services/#integration-health-as-a-loxep-feature) proposes it, Phase 6 assumes it exists, Phase 7 assumes it exists, and it has never been built. The second is **uptime monitoring**, a mature product category with two strong self-hosted answers.

The distinction survives the obvious objection. Probing Beszel's `/api/health` looks like uptime monitoring, but the subject is a registered Loxep record with a known provider and a documented health path, not a free-text URL — and the reason for the probe is that Loxep's own read adapter depends on it. **If a milestone ever ships a form whose first field is a URL the operator types, the line has been crossed.** That is the test to apply in review.

The stronger version of this argument is that a Loxep-run probe *cannot check the one thing that matters most*: whether Loxep is up. Gatus can, because it is a separate process. Which leads to the recommendation that gives this phase its best return.

## Publish Loxep's own health outward

Gatus exposes exactly one write path in its entire route table:

```text
POST /api/v1/endpoints/:key/external?success=<bool>&error=<msg>&duration=<ns>
     Authorization: Bearer <token declared in gatus YAML>
     key format:  <GROUP_NAME>_<ENDPOINT_NAME>
```

The endpoint must already be declared in Gatus's YAML under `external-endpoints` with its own bearer token, optionally with `heartbeat.interval` so the endpoint goes down on its own if no push arrives. It cannot create endpoints, and it cannot change configuration.

That is a near-perfect fit for the self-monitoring problem, and it runs the integration in the direction nobody expects:

```text
Loxep  ──(one POST per push, per subject)──>  operator's existing Gatus
                                                     |
                                              Gatus's own alerting
                                                     |
                                                   ntfy

If Loxep stops pushing, the heartbeat interval expires and Gatus
raises the alert Loxep could never have raised about itself.
```

What Loxep would publish is the state only Loxep knows: worker backlog, order-sync freshness per connection, notification delivery success, the reconciler's drift count, migration/readiness state. None of it is inventable by an external probe of `/health/ready`.

**Cost:** one outbound job, one bearer token in `application_secrets`, one configuration form. No new table, no new domain concept, and a hard cap on blast radius — a compromised token lets an attacker mark a Gatus endpoint healthy, and nothing else.

This is the cheapest genuinely new capability in the phase and it should ship before any reader.

### Gatus, in detail

Gatus is the only candidate whose integration is worth building in both directions, and its constraints are sharp enough to design around now.

- **Configuration is files, and Loxep must not write them.** Gatus reads `config/config.yaml` or, when the path is a directory, deep-merges every `*.yaml` beneath it, polling for changes every 30 seconds. Loxep owning `50-loxep.yaml` in a shared volume is technically clean and is exactly the trap: writing configuration files onto a host is configuration management, the fourth row of the inherited line. **Loxep does not push Gatus configuration.** The operator authors endpoints; Loxep reads them and links to them.
- **The read adapter must branch on the auth mode.** `/api/v1/endpoints/statuses` sits behind `security`. Basic auth is header-based and machine-consumable; OIDC resolves a client from a **session cookie**, with no bearer path — so against an OIDC-secured Gatus a server-to-server reader **cannot authenticate at all**. `GET /api/v1/config` is unauthenticated and returns `{ oidc, authenticated }`, which makes it the probe the adapter uses to decide what it can do. Against OIDC it degrades to the unprotected per-endpoint uptime and response-time routes, which requires knowing endpoint keys in advance — i.e. to `external_resources` rows the operator created. **The UI must say which mode it is in.** Silent degradation to a partial view of a status page is the failure mode that makes an operator trust a green dashboard that is not looking at everything.
- **Alert evidence, if it ships, has no schema negotiation.** Gatus's `custom` provider has no default body: the operator supplies the URL, method, headers, and body template, and Gatus substitutes `[ENDPOINT_NAME]`, `[ENDPOINT_GROUP]`, `[ENDPOINT_URL]`, `[RESULT_ERRORS]`, `[RESULT_CONDITIONS]`, `[ALERT_TRIGGERED_OR_RESOLVED]`, `[ALERT_DESCRIPTION]`. Loxep therefore **publishes the exact JSON contract it wants to receive** and documents the snippet to paste, rather than parsing somebody else's schema. That is the cleanest webhook relationship in the whole candidate set.

### Beszel, in detail — AMENDED 2026-08-13

**The first version of this section rested on a claim that is false, and the correction upgrades the verdict.** It is left visible rather than quietly rewritten, because the reasoning that produced it — inferring a credential model from a third-party widget's documentation instead of the vendor's own — is the mistake worth not repeating.

**What was claimed:** *"A read consumer needs a superuser credential. There is no scoped read-only token; third-party precedent (Homepage's Beszel widget) documents username/password of an admin-equivalent account."* Everything downstream of that — the tier-3 gate, the warning that a database compromise yields fleet-wide administrative control, the instruction that the form must not say "API token" — followed from it.

**What upstream actually documents.** Beszel publishes three roles in the ordinary `users` collection, and the lowest is exactly the credential this integration wants: *"Read-only users cannot create systems but can view any system shared with them by an admin and create alerts."* Upstream further states that *"regular user accounts and PocketBase superuser accounts are entirely separate"* and that *"changing a user's role to admin does not create a superuser account"* — the `users` collection and the `_superusers` collection are different credentials, reached through different auth endpoints. The REST guide's own first example authenticates *"as regular user"*.

So the corrected facts, in order of weight:

1. **A read consumer needs a `readonly` user, not a superuser.** Loxep authenticates against `POST /api/collections/users/auth-with-password` and never touches `_superusers`; `@loxep/integration-beszel`'s boundary test asserts that collection name never appears in a request URL. The blast radius of a Loxep database compromise plus keyring access is therefore *a view of the systems an admin deliberately shared with that account* — not administrative control of the monitoring hub. That is a materially smaller trade than the one open question 3 asked the owner to accept, and it is why the answer could be yes.
2. **The honesty requirement survives, redirected.** The original warning was that a field labelled "API token" over a superuser password *"is the kind of small dishonesty that later gets someone to reuse a password"*. That still binds — Beszel has no API token of any kind — so the connection form says **"Beszel readonly user"** and asks for an email and a password. The bundle is `beszel_credentials { email, password }`.
3. **Pre-1.0 after two years, with an explicit shape warning — unchanged.** Upstream still states record shapes *"may change in minor releases"*. The adapter designs around it rather than merely absorbing it: only `id` is required at the boundary, every other field degrades to `null`, and one unreadable record is skipped rather than failing the whole fleet read. Upstream documents no schema for the `systems` collection at all, so `id`, `status`, and `users` are confirmed from the REST guide's own examples and **`name`, `host`, `port`, and `updated` are inferred and marked UNVERIFIED** until a live probe confirms them.
4. **`GET /api/health` is unauthenticated — unchanged.** Inherited from PocketBase, returning `{"status":200,"message":"API is healthy."}`. It remains the tier-2 surface, and the adapter exposes it as a probe callable before any credential is stored.

Beszel's alerting is Shoutrrr with native ntfy, so the detection-and-delivery path is already complete without Loxep. Iframe embedding is effectively unsupported upstream; link out.

**Implementation status — the connection-level probe (loxep-rf4) and the per-system discovery/attach/health projection (loxep-y64, all three slices) are all BUILT.** The two-step probe (`health()` then one `listSystems()` page — `/api/health` alone would report `ok` over a garbage password) writes the connection's own `integration_health` row and, on success, doubles as the discovery read: `@loxep/app`'s `projectBeszelSystems` upserts one `external_resources` row per system (`upsertExternalResource`, keyed on the PocketBase record id) and one per-system `integration_health` row (`subject_type='external_resource'`, `source='adapter'`, status mapped from the system's own up/down/paused string — see `fleet-health.ts`'s `beszelSystemHealthStatus` for the exact, deliberately conservative mapping, since upstream still publishes no enumeration). The operator-confirmed attach picker (`AttachDiscoveredResourceDialog` on `/infrastructure/fleet/$name`) is the only way a discovered system becomes linked — never a name join. The fleet-detail panel renders the verbatim status string, both clocks (Beszel's own `updated` and Loxep's read clock) when the row carries one, and a deep link. `diagnoseHostWitnesses` consumes this per-resource data with no code change of its own, since it was already keyed generically by `(subject_type, subject_id)`.

### Dockhand, in detail — AMENDED 2026-08-13

This section originally concluded *"tier 1, and no adapter"*. The owner overturned that on 2026-08-13, and the three arguments behind the original verdict are answered here one at a time — two of them by an owner ruling, one by re-reading the source that was previously refused.

**The verification objection is resolved by a ruling about scope, not by ignoring the maintainer's wish.** The original reasoning was that Dockhand's repository prohibits AI/LLM ingestion, so Loxep's usual method — coding agents reading upstream source — is unavailable. The owner's ruling is narrower than the objection assumed: **the no-AI-ingestion wish covers source, not published documentation.** Dockhand's Mintlify site is the vendor's own published API reference, offered for exactly this purpose, and it is the sanctioned primary source. Every path, field, and default in `@loxep/integration-dockhand` is transcribed from it; **no Dockhand source was read.** That is a real constraint on the adapter's confidence and it is recorded in the package rather than assumed away.

**The auth contradiction dissolves on reading the reference.** The original claim was that *"API documentation … describes session-cookie auth while the manual describes API tokens — a contradiction that cannot be resolved without reading source."* The API reference is not contradictory: it documents *"HTTP-only session cookies"* obtained from `POST /api/auth/login` and sent back as `Cookie: session=…`, and it names no API key, personal access token, or service account anywhere. So Loxep stores a login (`dockhand_credentials { username, password }`), not a key.

**The stability objection stands, and is designed around rather than dismissed.** There is still no OpenAPI document and the `/api` base path is still unversioned. What upstream does offer is an explicit promise — *"The API currently does not use versioning. Breaking changes are avoided, and new fields are added in a backward-compatible manner"* — which is weaker than a version and stronger than the "informal" the original text credited it with. The adapter treats every response field as optional except an identifier, accepts **both** documented list envelopes (the overview says list endpoints *"return arrays directly without wrapping"*; the containers page documents a wrapping `containers` field, and the documentation cannot say which is real), and marks the whole surface UNVERIFIED until a live probe.

**The verbs objection is answered by the carve-out, and only by the carve-out.** It remains true that most of Dockhand's endpoints are mutations Loxep must never call, and the original sentence — *"an adapter that deliberately refuses them is a worse Dockhand embedded in Loxep"* — is still the right instinct about container lifecycle. What changed is that one Dockhand resource is not a lifecycle verb at all:

```text
/api/environments…    Dockhand's OWN INVENTORY of managed hosts. Writing one
                      creates a row in Dockhand's database. Registering a new
                      VPS is desired state, and Loxep already has a reconciler
                      for desired state.

everything else       acts on a Docker daemon. Forbidden, permanently.
```

So the shipped shape is a **read surface plus a host-registration intent surface**, and the deep-link argument survives untouched for everything else: a fleet panel shows what is running and links out, and the buttons that start and stop it live in Dockhand with the operator's own session and Dockhand's own RBAC.

What ships, concretely:

- **Read:** `GET /api/environments`, `GET /api/containers?env={id}&all={bool}`, `GET /api/stacks?env={id}`.
- **Host intent:** `GET`/`POST /api/environments`, `PUT /api/environments/{id}` — a `read`/`apply`/`capabilities` triple matching the DNS and mail ports, driven by `@loxep/infrastructure`'s `ContainerHostProviderPort`. **No delete.**
- **Forbidden and asserted:** container lifecycle, exec, logs, terminal, file browse, stack deploy/update/delete/git-sync, image pull/push/prune, network and volume creation, schedules, auto-update. `test/forbidden-verbs.test.ts` asserts both the exported surface and the actual traffic.
- **Secrets never round-trip.** A managed-host record can carry `tlsCa`/`tlsCert`/`tlsKey` PEM bundles and a `hawserToken`. The adapter's parse schema does not declare them, so they cannot survive parsing; the Loxep fact carries **presence bits** instead, and the reconciler compares that material by presence and never by value. A private key therefore cannot reach a diff, a run-step summary, or an error detail.
- **The join key is the host NAME**, not a stored provider id — Loxep's `hosting_targets_name_uq` and Dockhand's *"unique display name"* on the other side. That is what lets the whole seam ship **without a migration**, and its cost is recorded: a rename on either side surfaces as one create plus one unmatched observed host, deliberately visible rather than silently duplicating.
- **The login is rate-limited more heavily than reads.** Upstream locks an account out after *"5 failed attempts per IP/username combination"* with an *"exponential backoff (5-60 seconds)"*, so the adapter charges a login four budget tokens against a burst of eight and never retries more than once — a loop would convert a transient rejection into a fleet-wide outage of Loxep's Dockhand reads.

**Licensing is not the blocker — unchanged.** BSL-1.1 with a 2029 conversion to Apache-2.0, and the additional-use grant explicitly permits internal business use and *"embedding or integrating the Licensed Work into internal tools or platforms that are not offered commercially to third parties"*. Loxep calling Dockhand's API is permitted; only offering a commercial hosted Docker-management service would not be.

Dockhand's outbound generic webhook and ntfy channels remain available for tier 4 evidence ingestion on the same terms as everything else.

**AMENDED 2026-08-16 (`loxep-bub`) — the host-intent record's `host`/`publicIp` now also feed the typed address model.** For a Dockhand environment linked to a hosting target, `projectDockhandResources` lands a value that parses as a real IP literal into `host_addresses` as `kind = 'other'` (heuristically unclassified — this is exactly the owner's own observation, *"most of dockhand is showing tailscale ip, which might not be the most helpful in all scenarios"*, given a home), `provenance` `observed:dockhand`/`observed:dockhand.public_ip` so the two fields never collide under one slot. `host` is a connection address and is very often a hostname, not an IP — the write is skipped rather than attempted malformed. See [Infrastructure Control Plane Design](../infrastructure-control-design/#milestone-3-fleet-token-scope-and-the-infrastructure-workspace-loxep-lmy3)'s own amendment for the full model, including why an observed row can never reach the DNS materializer regardless of how it is later classified.

### Tailscale and Termix, in detail — AMENDED 2026-08-13

Neither tool had a verdict section before today; each appeared only as a row in [the link vocabulary table](#the-link-model-and-its-vocabulary), which is this design's tier-1 default for a companion the product docs recommend ([Companion Services](../../product/companion-services/#infrastructure-operations) lists Tailscale under "private networking/VPN" and TermixSSH under "terminal/SSH access management") but that no one had yet checked against a published API. Both checks are done now, and both overturn the default.

**Tailscale.** The owner-supplied primary source, https://tailscale.com/docs/reference/tailscale-api, now redirects to an interactive, JavaScript-rendered API explorer this environment could not fetch as readable text. What it and its supporting artifacts still establish, corroborated against Tailscale's own maintained Go client (`tailscale.com/client/tailscale/v2`) and its OAuth-clients documentation:

1. **Two documented machine-usable auth modes, and neither subsumes the other.** A personal access token, generated from the admin console's Keys page by an Owner/Admin/IT admin/Network admin, sent as HTTP Basic auth (token as username, empty password) — but it *"automatically expire[s] after the chosen number of days"* (1–90, operator's choice) with **no auto-renewal**, which is the operational implication worth stating plainly: unattended polling eventually needs a human to paste a fresh one. An OAuth client (`client_id`/`client_secret`, RFC 6749 §4.4 client-credentials) avoids that — its minted access tokens *"expire after one hour"* and the adapter re-exchanges them automatically — at the cost of a second setup path. `tailscale_credentials` is a discriminated union rather than picking one, because both are the provider's own documented way in.
2. **No whoami/identity endpoint exists.** The Go client's `Client` exposes `Contacts`, `DNS`, `DevicePosture`, `Devices`, `Keys`, `Logging`, `PolicyFile`, `Services`, `TailnetSettings`, `Users`, `VIPServices`, `Webhooks` — nothing named `WhoAmI`/`Me`. Unlike Beszel's genuinely unauthenticated tier-2 health path, Tailscale requires the credential for even its cheapest read, so `probe()` substitutes the devices list itself and reports `{reachable, authenticated}` from its outcome rather than throwing on a 401/403.
3. **No published rate limit.** An upstream feature request asking for one to be documented (github.com/tailscale/tailscale#14328) was still open as of 2026-08-13. The adapter's local budget is therefore a politeness default, the same posture Beszel's and Dockhand's equally-undocumented ceilings take.
4. **Read-only by construction, not by credential scope.** The `devices:core` OAuth scope grants read AND write together — Tailscale publishes no device-mutation-free scope narrower than that — so the restraint is entirely in the adapter's own exported surface (no member named after a write verb) and its path allow-list, asserted by a boundary test in the same style as Dockhand's `forbidden-verbs.test.ts`.

**Termix.** The owner-supplied primary source, https://docs.termix.site/api/termix-api/, is a Docusaurus + `docusaurus-openapi-docs` site this environment could fetch only as navigation chrome. Its generating source is public — `Termix-SSH/Docs`'s `static/openapi.json`, a full OpenAPI 3.0.3 document, 274 paths, last regenerated 2026-08-06 ("feat: update API docs for 2.6.1") — and settles what the rendered page could not:

1. **Reads exist and are reachable.** `GET /host/db/host` ("Retrieves all SSH hosts for the authenticated user"), `GET /status` ("Retrieves the status of all hosts… A map of host IDs to their status entries"), and a fully-specified `GET /open-tabs/active-sessions` ("Returns live terminal sessions from the session manager, both sessions the caller owns and SSH sessions shared to the caller by another user"). This is the fact that settles the bd issue's own open question: the docs prove reads are usable, so the adapter ships rather than falling back to link-only.
2. **Two of the three response shapes carry no documented schema anywhere in the spec.** Every error response across all 274 operations is description-text only, and `GET /host/db/host` / `GET /status` are no different for their success bodies. `name`/`ip` on a host record and the connectivity/last-seen keys on a status entry are therefore UNVERIFIED, plausible guesses read defensively — the same posture `@loxep/integration-dockhand`'s `environmentSchema` takes toward its own undocumented fields — and `test/live-termix.test.ts` is the standing job to replace the guess with observed fact.
3. **Auth is username/password, not a token**, exchanged at `POST /users/login` for a JWT. The spec's own auth story is internally inconsistent — its global `security: [{bearerAuth: []}]` applies to every operation with no per-route override, including login itself, which cannot literally require the JWT it is about to issue — so the adapter treats login as the one unauthenticated exception the spec should have declared. When the login body carries no usable token (its own response schema is undocumented), the adapter falls back to `GET /users/me/token`, whose description — *"Intended for mobile WebView clients that cannot read HTTP-only cookies"* — describes precisely a headless server-to-server adapter's situation.
4. **Termix publishes no scoped read-only role**, unlike Beszel's `readonly` collection. The stored account is a real Termix user; Loxep's restraint against Termix's much larger write surface (Docker container control, systemd services, process signals, terminal exec, file deletion — an order of magnitude larger danger surface than Dockhand's) is enforced entirely in the adapter's own exported surface and an enumerated forbidden-path-segment list, never by anything the account's permissions withhold.

One documentation-hygiene note worth recording rather than silently working around: `Termix-SSH/Docs`'s individual per-operation `.mdx` pages (what a human browsing docs.termix.site actually sees) were last regenerated 2026-01-13 and have drifted from the `openapi.json` they were generated from — `get-all-ssh-hosts.api.mdx` still shows the path as `/ssh/db/host`, while the current spec has it at `/host/db/host`. The adapter follows the spec.

Both integrations' alerting/notification surfaces (if any) are out of scope for this milestone, matching how Beszel's and Dockhand's own notification channels were left to the operator rather than routed through Loxep.

**AMENDED 2026-08-16 (`loxep-bub`) — a linked Tailscale device's addresses now land in the typed address model too.** `projectTailscaleDevices` writes/refreshes `kind = 'tailnet'`, `provenance = 'observed:tailscale'` `host_addresses` rows for a device's linked hosting target, one per address family the device reports — the "Private network" row above still reads the SAME sync's link metadata, unchanged; this is an additional, typed destination for the same fact, not a replacement. The `address_v4`/`address_v6` prohibition this design's own [Tailscale, in detail](#tailscale-and-termix-in-detail--amended-2026-08-13) section inherits from the DNS materializer no longer needs a "suggest, don't overwrite" workaround: the tailnet kind is structurally quarantined from that pair by construction, so writing one is never writing the other. See [Infrastructure Control Plane Design](../infrastructure-control-design/#milestone-3-fleet-token-scope-and-the-infrastructure-workspace-loxep-lmy3)'s own amendment for the full model.

### Netdata, and why the best API here is still not an adapter

Netdata has the strongest machine interface of the six and should still be linked rather than read, for one reason that is architectural rather than technical:

**there is no credential to store.** Bearer-token protection on the agent requires the agent to be *claimed to Netdata Cloud with an active connection*; tokens are issued through a Cloud redirect and cannot be obtained offline. A purely self-hosted, unclaimed agent's API is protected by IP allowlists in `netdata.conf` or by a reverse proxy — that is, by network position. A Loxep "connection" for Netdata would be a base URL with an empty credential bundle, which misrepresents the [configuration and secrets model](../configuration-and-secrets/#secret-handling-rules) rather than fitting it.

Two supporting reasons: Netdata and Beszel occupy the same slot, and an installation running both does not need two Loxep adapters — **pick at most one metrics adapter, ever**. And the data Netdata exposes is per-second time series, which Loxep is forbidden to store.

What Loxep should record, if the design is implemented: the v3 endpoint set (`/api/v3/nodes`, `/api/v3/alerts`, `/api/v3/alert_transitions`), because Netdata's own OpenAPI states *"V1 and V2 APIs are deprecated… New integrations should use V3 exclusively"* and the `/api/v1/alarms` family is gone from the specification entirely. Any future adapter targets v3. The agent dashboard iframes cleanly (`x-frame-options` defaults to empty), so an embed is available if a later surface wants one.

## `integration_health`: the only new table

[Companion Services](../../product/companion-services/#integration-health-as-a-loxep-feature) sketched this table. [Phase 6](../services-billing-schema-design/#external-resource-integration-surfaces) says its companion integrations *"reuse the `integration_health` subject model… No new table."* Phase 7 lists the overlap between it and `managed_domains`' private health columns as an unresolved tension. **Three designs assume a table that does not exist.** Phase 8 is where it gets built, because Phase 8 is the first phase whose entire value proposition is health rollup.

```text
integration_health
subject_type            text not null
subject_id              uuid not null
status                  text not null
source                  text not null
checked_at              timestamptz not null
last_success_at         timestamptz null
last_failure_at         timestamptz null
consecutive_failures    integer not null default 0
detail                  jsonb not null default '{}'
updated_at              timestamptz not null
primary key(subject_type, subject_id)
check(subject_type in ('connection','notification_endpoint','storage_backend',
                       'external_resource','hosting_target','managed_domain'))
check(status in ('ok','degraded','failing','unknown'))
check(source in ('probe','adapter','ingest','report'))
check((status = 'ok') = (consecutive_failures = 0))
```

The decisions worth arguing:

- **One row per subject, overwritten in place.** This is the phase's enforceable boundary marker. An append-only health table with a `checked_at` key is a time series, and a time series of host status is the product Loxep must not build. The primary key *is* the upsert probe, so a sweep is idempotent by construction, matching the discipline `dns_drift_findings` uses for its unresolved partial unique.
- **No surrogate key.** `(subject_type, subject_id)` is total and stable; a uuid on this row would exist only to be ignored. The precedent is `resource_links`, which carries no surrogate key for the same reason.
- **`subject_id` is deliberately not a foreign key**, because it is polymorphic across six tables. This is a real cost, honestly stated: nothing stops an orphan row when a connection is deleted, and the owning service must clear its own health row in the same transaction as the delete. The precedents are `reconcile_runs.subject_id` and `journal_entry_source_links`, both of which made this trade for the same reason. It is the one place this design accepts weaker integrity than the rest of the schema, and the mitigation is a service rule with a test, not a constraint.
- **`source` distinguishes how the row was learned**, which changes how it should be read. `probe` means Loxep checked. `adapter` means Loxep read a tool's API. `ingest` means a webhook told us. `report` means an out-of-band push (a backup job's success callback). A `report` from a tool that has since died goes silently stale, so **staleness is derived from `checked_at`, never asserted as a status** — there is no `stale` value. This is the same discipline Phase 7 applied when it refused to make `degraded` a state.
- **`integration_health` never drives retry or backoff.** That resolves the Phase 7 tension rather than papering over it: `managed_domains.consecutive_errors`, `connections.last_error_at`, and `monitor_targets.backoff_until` stay authoritative for their own retry behavior, and this table is a **derived rollup** for display and for deciding whether anything needs attention. Two copies with different jobs, one of them derived from the other, is [cross-domain rule 4](../domain-boundaries/#cross-domain-rules), not duplication. **Nothing may be dropped from the owning tables when this ships** — see [open questions](#open-questions).
- **`detail` is the one jsonb, and it is small, Loxep-owned, and redacted.** Counts, a short message, an error taxonomy kind. Never a provider response body, never a header, never a URL carrying credentials. The contract permits raw payloads only at explicit provenance boundaries, and this is not one. Per-adapter redaction follows the [ADR-0021](../../decisions/0021-order-payload-retention/) `redact*` precedent.
- **`check((status = 'ok') = (consecutive_failures = 0))`** is a cheap cross-column invariant in the same spirit as `order_fees`' scope check: a green row with a failure streak is a bug that would otherwise render as a green dashboard.

**Ownership: shared foundation, not Infrastructure.** Four of its six subject types are foundation records that have nothing to do with the fleet, and two other phases already depend on it. It lives in `@loxep/domain` alongside the connections, settings, and secrets services. Infrastructure and the fleet are *consumers*, exactly as Commerce is a consumer of the shared scheduling model.

### Status transition tracking — AMENDED 2026-08-13 (loxep-oii)

Weave audit 2026-08 finding 5 flagged a gap this design left open: before this amendment, `upsertHealth` overwrote `integration_health` in place with no prior value, so a status degradation (or recovery) could never be noticed after the fact once the next probe ran — "cheap to fix now, impossible to backfill later." Migration `0020` adds two nullable columns, written by `upsertHealth` alone:

```text
previous_status      text, nullable      the status immediately before the most recent transition
status_changed_at    timestamptz, nullable   when that transition was observed
```

Both are set together, only when the incoming `status` differs from the stored row's `status`; an unchanged-status upsert leaves both alone — they track the most recent *transition*, not the most recent write, and stay null until a subject's first transition. This is explicitly **not** the health history table the "what Phase 8 does not create" list above still refuses: one prior value per subject, replaced at the next transition, not an append-only series. The one-row-per-subject shape and the primary-key-as-upsert-probe property are unchanged.

Three `CHECK`s extend this table's existing biconditional discipline (the `(status = 'ok') = (consecutive_failures = 0)` precedent) to the new pair, so a nonsensical row is refused at the database level rather than trusted to the one call site: `previous_status` is one of the same closed statuses when present; `previous_status` and `status_changed_at` are null together, never one without the other; and `previous_status`, when present, differs from the current `status` — a "transition" that didn't change anything is a bug, the same category the `ok`/`consecutive_failures` check already guards against.

`/settings` overview's Integration health table (`IntegrationHealthReport`) renders a "Changed" column off `status_changed_at` (relative time, with the previous status in its tooltip), alongside the existing "Last checked" column.

**What this amendment deliberately does not do:** wire the transition into `notification_deliveries` or any rule model. That is the other half of weave audit finding 5 — the schema-bound-to-market-events gap — and remains open, tracked as the remaining scope of loxep-oii. This amendment makes the transition **observable**; making it **notifiable** is separate, larger work gated on the `market_event_id` design decision the finding also names.

**Resolved 2026-08-15 (loxep-oii, [ADR-0023](../../decisions/0023-notifiable-events-and-delivery-subjects/), migration `0022`).** The ledger is now subject-neutral (`notification_events`), and `runHealthSweep` records a `health`-class event for each transition it observes. Two things this phase argued for survived the generalization **structurally**, not by omission:

- **Only Loxep's own integration subjects are notifiable** — `connection`, `notification_endpoint`, `storage_backend`. The fleet subjects (`external_resource`, `hosting_target`, `managed_domain`) are excluded by the event-class registry itself (`NOTIFIABLE_HEALTH_SUBJECT_TYPES`), so open question 1's ruling — companion tools alert their own operators through ntfy, and Loxep does not become a slower relay — is enforced by the code that would have to break it, and asserted by test. The rule at the top of `fleet-health.ts` ("no fleet probe writes a `notification_deliveries` row") is unchanged and now true by construction.
- **The Gatus heartbeat endpoint is still not an `integration_health` subject at all** (Binding Rule 1, the self-latching loop), so `gatusPushSetting.endpointKey` cannot become a notification event through any path.

Transitions into or out of `unknown` are never emitted: "we could not tell" is not an alert.

**Ignore's mechanism is a deliberate, recorded deviation from loxep-50t §4's own recommendation, not an oversight.** §4 names two options and recommends the first: `external_resources.metadata.ignoredAt` (a Loxep-owned annotation on the device's own row) as the PRIMARY choice, with an `integration.tailscale.ignored_devices` settings map as an "acceptable alternative... record the second so the choice is visible." The settings map (`@loxep/domain`'s `tailscaleIgnoredDevicesSetting`, keyed by the device's own tailnet node id rather than the internal row id, so a dismissal survives the row being re-upserted) is what shipped instead. Three rules carry over unchanged and one is added:

- **`metadata` holds sync metadata only** — last-observed instant, the tool's own status string, an ETag. Never a copy of the tool's data. The moment a container list is authoritative in two places, one of them is stale.
- **Direction of authority is fixed per purpose.** Every purpose in the table above is *tool-authoritative*: Beszel owns host metrics, Gatus owns uptime results, Dockhand owns container state. Loxep records the link and the latest status, and nothing more.

  **AMENDED 2026-08-13:** the original sentence continued *"Not one purpose in this phase makes Loxep authoritative — which is the tell that the phase is on the right side of the inherited line."* The [host-registration carve-out](#amended-2026-08-13--the-host-registration-carve-out-stated-precisely) makes exactly one thing Loxep-authoritative: **which machines a container manager should know about.** That is not a new tell that the line was crossed — it is the Phase 7 relationship, where Loxep owns declared intent and the provider holds it — but it does mean the phase can no longer be checked by the simple test "is anything Loxep-authoritative?". The replacement test is the carve-out's own: *does this call cause code to run on a managed host?* Container state remains Dockhand-authoritative, permanently.
- **No provider-specific column anywhere.** There is no `hosting_targets.beszel_system_id`, and the host reconciler does not need one: it matches on the host **name**, which is already unique on both sides (`hosting_targets_name_uq`, and Dockhand's *"unique display name"*). That is what let the seam ship with no migration; the cost is that a rename on either side surfaces as an unmatched host rather than being followed automatically.
- **New:** a link is what makes a tool's health *attributable*. A Gatus endpoint failing is interesting; a Gatus endpoint failing that is linked to the hosting target three managed domains point at is the fleet view [Workspaces](../../product/workspaces/#infrastructure-is-a-future-peer-root-and-it-is-about-the-installation-itself) reserved the workspace for. The correlation is the product; the link row is the whole mechanism.

**The known-tool registry is code, not schema.** Each supported provider needs an icon, a label, a documented health path (`/api/health`, `/ping`, `/health`), and whether it is embeddable. That is a small typed constant in `@loxep/domain` keyed by `provider`, in the shape of the integrations catalog — never a table, and never a column on `external_resources`.

**Link-only tools do not get an integrations-catalog card.** `/settings/integrations` is the catalog of services Loxep *integrates with* — a card there implies an account, a credential, and a connection. A Cockpit deep link has none of those. Link-only tools are created from an "Add tool link" form on a fleet record and documented under Guides. Only tiers 3 and 4 earn a catalog entry, because only they create a `connections` row.

## Connections, credentials, and reachability

Tier 3 tools are ordinary provider connections, created in-app and never in Compose:

```text
connections.provider = 'gatus' | 'beszel' | 'dockhand' | 'tailscale' | 'termix'
connections.config              base URL; for Gatus, the observed auth mode;
                                for Tailscale, the tailnet name (default '-')
connection_credentials          gatus_credentials     { username, password }  (basic auth)
                                beszel_credentials    { email, password }     (READONLY hub user)
                                dockhand_credentials  { username, password }  (session login)
                                tailscale_credentials { mode: 'api_access_token', apiAccessToken }
                                                     | { mode: 'oauth_client', clientId, clientSecret }
                                termix_credentials    { username, password }  (login, no scoped token)
application_secrets             infrastructure.gatus_push.<id>  { token }    (outbound push)
```

- The base URL is **non-secret connection config**, exactly as a WooCommerce store URL is, and for the same reason: it must stay readable without a decryption round-trip. For Dockhand and Termix it is stored as the **origin**, with the unversioned `/api`-style prefix owned by the adapter — a pasted URL ending in the prefix is normalized rather than doubled. Tailscale has no per-deployment base URL (SaaS default `api.tailscale.com`); its non-secret config is the tailnet name instead.
- **Every login-shaped credential here is a login, and not one of them is an API token**, because not one of those tools issues one. The form labels must say so. The original warning here was about labelling a superuser password an "API token"; the correction to the Beszel verdict does not retire that warning, it generalizes it — Beszel's field is a readonly user, Dockhand's and Termix's are session logins, and a form implying otherwise is the same failure. Tailscale is the one exception in this table that genuinely IS a token (or an OAuth client), and its form says so accordingly.
- **Dockhand's account should hold four permissions and no more:** `environments:view`, `environments:edit`, `containers:view`, `stacks:view`. It must not be the operator's own admin account. Loxep's restraint lives in its own adapter surface, not in Dockhand's session — a session that can list containers can also start them, which is precisely why the [forbidden-verbs test](#dockhand-in-detail--amended-2026-08-13) exists. **Termix has no equivalent narrower role to grant at all** — see [its detail section](#tailscale-and-termix-in-detail--amended-2026-08-13) — so the same restraint there is enforced entirely in code, with nothing narrower to ask the operator to configure on Termix's side.
- **Dockhand's login is the rate-limited endpoint**, not its reads: upstream locks out after five failed attempts per IP/username pair. A stored credential that has gone stale must therefore fail loudly and stop, never retry in a loop. Termix documents a `429` on login too, with no published numeric threshold; the adapter charges its login a higher rate-budget cost than an ordinary read for the same reason.
- **Tailscale's access token expires on a fixed schedule with no auto-renewal** (1–90 days, operator's choice) — the one credential in this table that fails not from being wrong but from time passing. **At the adapter boundary**, Loxep still cannot tell the two apart: a bare HTTP 401 gives `probe()` no way to distinguish "the correct credential aged out" from "the credential was always wrong", so both surface as an ordinary `auth` error there. **Above that boundary, loxep-50t closes the gap the design originally left open:** an operator can record the expiry Tailscale showed at generation time (`connections.config.tailscale.credentialExpiresAt`), and the connection probe returns a distinct `degraded` status — never `failing`, never a fabricated "expired" state the adapter cannot prove — once that recorded date is within 14 days or has passed, ahead of the eventual 401. The connections table also shows an explicit "expiry not recorded" warning rather than a false green when no expiry is on file. This is honest specifically because it rests on an operator-supplied fact, not an adapter inference: the read still succeeding after the recorded date passes means either the date was wrong or the token was quietly rotated, and the copy says so rather than picking a side.
- **Reachability is a deployment fact this design must not assume.** These hubs commonly live on a private network, behind a tunnel, or on a Tailscale address. Loxep reaching them is not guaranteed by the fact that a human's browser can. Every tier-2 and tier-3 subject must therefore render "unreachable from Loxep" as a **distinct, explained state**, not as `failing` — otherwise a network topology problem reads as a fleet outage. This is the most likely first-day support question in the whole phase.
- No adapter may follow a redirect to a different host, and no adapter may send its credential to a URL it did not construct from stored config.

## Probing, jobs, and where cadence lives

```text
health.sweep         one recurring Graphile Worker job
                     reads integration_health + the subject registry
                     probes only subjects whose next check is due
                     upserts one row per subject
```

**Recommendation: a single recurring sweep, and no `monitor_targets` rows.** Phase 7 registered a target type against the shared scheduling model because a domain's reconcile cadence is genuinely per-subject and operator-tunable. Health probing is neither: the cadence is uniform, there is no per-subject intent worth an operator setting, and the contract's rule is specifically against *one permanent cron per monitored item* — one cron for the whole sweep is the shape the contract prescribes.

Due-ness and backoff need no extra column. `checked_at` and `consecutive_failures` are already on the row, so the sweep computes the next check as `checked_at + interval(consecutive_failures)` and skips what is not due. A dead host backs off to a long interval on its own, and the state that drives the backoff is the same state the UI renders.

Phase 7's [open question 5](../infrastructure-control-design/#open-questions) asks the same question for reconcile cadence and reaches a different answer. That is not a contradiction — the cases genuinely differ — but the owner should answer both together, because answering them inconsistently for bad reasons is easier than answering them differently for good ones.

Handlers are idempotent by the primary key. A probe carries no credential in its job payload: it passes the subject key and resolves the credential inside the task, per Configuration & Secrets rule 5.

## Evidence ingestion, if it ships

**IMPLEMENTED 2026-08-15 (loxep-ovj.7), owner-approved.** Open question 4 is answered yes, narrowly: the endpoint, auth model, and no-new-table shape below shipped exactly as sketched, plus one refinement this section left implicit and one deliberate scope boundary, both recorded here rather than discovered later:

- **An evidence-ingest connection is always its own dedicated `connections` row, never a tier-3 read connection wearing a second hat.** `kind = 'evidence_ingest'` (`@loxep/domain`'s `EVIDENCE_INGEST_CONNECTION_KIND`) marks it. The reason is a race this section's sketch does not mention: `subject_type='connection', subject_id=:connectionId` is the SAME key `health.sweep`'s own derived `connection` probe already writes for every non-archived connection (`source='probe'`, `unknown`/`never_succeeded` for anything with no adapter) — reusing a tier-3 row would let that sweep silently overwrite the webhook's `source='ingest'` row within five minutes. `health-probes.ts`'s `listConnectionCandidates` now EXCLUDES every `evidence_ingest`-kind connection from the sweep entirely, the same "two writers of one subject" resolution this design already uses for Beszel/Tailscale/Gatus nulling `fleet-tool-registry.ts`'s `healthPath`. One consequence, stated plainly: an evidence-ingest connection's health never decays to `unknown` on its own when a sender goes quiet — staleness detection (the `ntfy alert if stale` half of [Companion Services](../../product/companion-services/#databasus)'s Databasus sketch) is NOT built by this milestone.
- **Provider normalizers shipped for Gatus and Beszel** (`@loxep/integration-gatus`/`@loxep/integration-beszel`'s `webhook.ts`), plus a GENERIC contract Loxep dictates for Databasus and any other sender with no shape of its own (`@loxep/domain`'s `normalizeGenericEvidenceWebhook`) — Netdata's and Dockhand's normalizers are not built; nothing prevents adding one later at the same integration boundary.
- **The feedback-latch is enforced, not just described:** `normalizeGatusAlertWebhook` computes the `<GROUP>_<NAME>` key an incoming alert's endpoint would produce (Gatus's own sanitization rule, re-verified) and drops — records as evidence, never projects — any alert matching the operator's configured `gatusPushSetting.endpointKey`, mirroring `gatus-push.ts`'s own BINDING RULE 1 for discovery.
- **`notification_deliveries` is untouched by construction:** `@loxep/app`'s `fleet-evidence.ts` imports nothing from `@loxep/notifications` and calls neither `recordNotificationEvent` nor `publishNotificationEvent`.
- **Settings surface:** `/settings/connections` gained an "Inbound fleet evidence" panel — name + sender kind, a mint-and-reveal-once dialog (ADR-0022, `RevealOnceDialog`'s pattern) showing both the webhook URL and the bearer token exactly once, and removal through the existing generic `deleteConnection`. Guides: [Sending fleet alert evidence](../../guides/fleet-evidence-webhooks/) documents the Gatus `custom`-provider YAML block and the Beszel/Databasus pointers.
- **Rate limit and size cap:** an in-memory, per-process, per-`connectionId` fixed-window limiter (30 requests/minute) and a 64KB body cap (checked via `Content-Length` before any read, then enforced again while streaming) — a documented trade-off given the contract's no-Redis rule, not a DB-backed limiter.

Everything above needs no inbound HTTP surface. Tier 4 does, and that surface **does not exist today**: `apps/web/src/routes/` has four API routes (Better Auth, the eBay OAuth callback, avatar upload, avatar fetch) and no webhook receiver. [Principle 15 and the contract](../../development/implementation-contract/#external-api) design *toward* a stable `/api/v1`; none is built.

So tier 4 is not a small addition to Phase 8 — it is the first inbound integration surface Loxep has ever had, and it should be judged as that:

```text
POST /api/v1/hooks/fleet/:connectionId
     Authorization: Bearer <per-connection ingest token>

  -> verify token against connection_credentials (constant-time)
  -> write ONE source_events row  (the existing inbound provenance envelope:
     connection identity, event type, external id, payload, payload hash,
     processing state) — no new table
  -> enqueue a job that projects it into integration_health with source='ingest'
  -> write NO notification_deliveries row, ever
```

Reusing `source_events` is the whole reason this costs no schema: it is *"the durable ingestion envelope [for] what an external provider delivered"*, with payload-hash deduplication already in it, and an alert webhook is exactly that. Retention follows [ADR-0021](../../decisions/0021-order-payload-retention/)'s per-object-class reasoning.

The security properties are the hard part, and they are why this is [OWNER-REVIEW-CRITICAL](#open-questions): the endpoint must be unauthenticated by session and authenticated by a per-connection bearer token; it must be rate-limited and size-capped before parsing; it must never echo the payload back; a bad token must not distinguish itself from an unknown connection in the response; and once the URL has been pasted into five tools' configuration, withdrawing it is a fleet-wide reconfiguration rather than a deploy.

Gatus makes this the most attractive it can be, because Loxep dictates the payload rather than parsing one. Beszel, Netdata, and Dockhand all offer generic webhooks with their own shapes, which means one small normalizer per provider at the integration boundary — never in the receiver.

/infrastructure/fleet/$name  a "Tools" panel per hosting target: every linked tool with

Three behaviors that are design constraints rather than presentation choices:

- **Every status renders its provenance.** "Beszel says this host is up, read 4 minutes ago" and "Loxep could not reach Beszel for 20 minutes" are different statements and must look different. A status with no visible age is a status an operator will over-trust.
- **A deep link opens the tool, not a Loxep copy of it.** No embedded container list, no metric chart, no proxied terminal. Where an embed is genuinely available (Netdata) it may be offered as an option; Cockpit's same-origin constraint and Beszel's lack of support mean it must never be assumed.
- **The Operations band keeps [its existing rule](../../product/workspaces/#dashboard-workspace): real data only.** A fleet with no linked tools renders as absent, not as green. "Nothing configured" and "everything healthy" must never look alike — on a fleet dashboard that confusion is the one that gets somebody paged at 3am for nothing, or worse, not paged at all.

## Migration plan sketch

One table, one migration, no alterations.

```text
1. integration_health   (no foreign keys; polymorphic subject by design)
```

Indexes — volumes are tens of subjects, not thousands:

```text
integration_health   primary key(subject_type, subject_id)      the upsert probe and the only lookup
integration_health   index(status) where status <> 'ok'         "what needs attention"
integration_health   index(checked_at)                          the sweep's due-work scan
```

Not indexed on purpose: `source` and `subject_type` alone — low cardinality, always accompanied by a subject or a status.

Which existing tables gain columns: **none.** `external_resources` and `resource_links` are used exactly as shipped; `connections` gains provider values, not columns; `application_secrets` gains purposes, which is what that column is for; `notification_deliveries`, `notification_rules`, and `market_events` are untouched by design.

**AMENDED 2026-08-13 (`loxep-uhs`) — one deliberate exception to "no alterations to existing Phase 0 tables".** `external_resources` shipped in migration `0000` with no unique constraint on `(provider, external_type, external_id)`, and `registerExternalResource` unconditionally INSERTs. Scheduled adapter-driven discovery (a Beszel systems read, a Gatus endpoints read, and so on) re-observing the same provider object on every sweep would duplicate a row every cycle — every per-resource slice this design's later milestones need (`loxep-y64`/`loxep-hb7`/`loxep-1au`/`loxep-50t`/`loxep-wvm`) depends on an idempotent write existing first. Migration `0021` adds a single **partial** unique index, `external_resources_provider_type_external_id_uq`, on `(provider, external_type, external_id) WHERE external_id IS NOT NULL` — partial, not total, because tier-1 operator-typed companion links legitimately carry a `NULL external_id` (a hand-entered URL has nothing to key on) and several such rows for the same `(provider, external_type)` must remain legal. `@loxep/domain` gains `upsertExternalResource` alongside the existing `registerExternalResource`, targeting the new index with `ON CONFLICT ... DO UPDATE`; tier-1 flows keep using `registerExternalResource` unchanged. This is the one column-free, index-only exception to the "no alterations" sentence above, made explicitly rather than silently smuggled into a later migration.

Verify at implementation time: Drizzle Kit support for a composite primary key with `CHECK` constraints referencing more than one column, and drop to hand-written SQL rather than weakening the invariant — the same instruction every earlier phase gives.

## Open questions

Each is a genuinely unresolved decision with a recommendation. **A recommendation is not an answer.** Items marked **OWNER-REVIEW-CRITICAL** are either irreversible in practice or are where the [Phase 7 non-goal tension](../infrastructure-control-design/#the-non-goal-this-design-runs-against) bites hardest.

1. **OWNER-REVIEW-CRITICAL — Does Loxep ever become the delivery path for infrastructure alerts?** This design says no: the tools detect and deliver to ntfy; Loxep records evidence.

   *Recommendation:* hold that line. Loxep runs on the fleet, so it cannot alert on its own outage, and ntfy already unifies the alert stream without Loxep in it. Making Loxep a relay would additionally require altering the shipped `notification_deliveries` ledger from market-event identity to a polymorphic subject — real work, undertaken to become a slower ntfy.

   *The owner must confirm:* that per-transport fan-out and Loxep-authored rules for infrastructure alerts are not wanted. This is marked critical because it is irreversible in the way that matters — once operators rely on Loxep for host alerts, the alert that never fires during a Loxep outage is unrecoverable, and removing the feature afterward is a trust event.

2. **OWNER-REVIEW-CRITICAL — Does Loxep run its own uptime probes?** This design says no for arbitrary endpoints and yes for registered subjects Loxep depends on.

   *Recommendation:* hold the subject-based line, and treat "a form whose first field is a URL the operator types" as the review test. Gatus and Uptime Kuma are mature, they run independently of Loxep, and one of them can watch Loxep itself.

   *The owner must confirm:* that endpoint monitoring stays a companion capability permanently. This is where the [Master Domain Map's non-goal](../../product/master-domain-map/#what-loxep-is-not) bites hardest, because uptime monitoring is the easiest thing in this phase to build and the least defensible.

3. **ANSWERED 2026-08-13 — May Loxep store a Beszel credential? YES, and the question was harder than it needed to be.**

   The owner answered yes, and stated the general rule it comes from: **credentials may be provided wherever an integration is worthwhile.** That alone would have settled it.

   But the question as originally posed — *"may Loxep store a Beszel **superuser** credential?"* — rested on a false premise, and re-verifying the owner-supplied primary source removed it. Beszel documents a `readonly` role in the ordinary `users` collection, entirely separate from PocketBase superusers. What Loxep stores is a purpose-made readonly account that sees only the systems an admin shared with it, so the *"fleet-wide monitoring-hub administrative access"* the owner was being asked to accept was never the actual price. See the [amended Beszel section](#beszel-in-detail--amended-2026-08-13).

   **Resolved as:** tier 3 ships. The bundle is `beszel_credentials { email, password }`, the form says "Beszel readonly user" and never "API token", the credential should be a dedicated account rather than the operator's own, and the adapter exposes no mutating member at all — a boundary test asserts every request is a `GET` apart from the login exchange, and that `_superusers` never appears in a URL.

   *Standing obligation:* the honesty requirement about the form label is not retired by the correction, only redirected. Beszel has no API token of any kind, and a form that implies otherwise is the same failure in the opposite direction.

4. **ANSWERED 2026-08-15 (loxep-ovj.7) — Does Loxep expose an inbound webhook receiver? YES, narrowly, as the opening move of `/api/v1`.**

   The owner approved a publicly reachable ingest path, on the terms this question's own recommendation set: authentication is a per-connection bearer token verified in constant time, an unknown connection and a wrong token are indistinguishable in the response, the route is rate-limited and size-capped before any parsing, and the payload is never echoed back. See [Evidence ingestion, if it ships](#evidence-ingestion-if-it-ships)'s implementation-status paragraph for exactly what shipped and the one deliberate scope boundary (no staleness decay for a quiet sender) left for later.

   *Standing obligation, unchanged by the approval:* once a webhook URL is pasted into an operator's Gatus/Beszel/Databasus configuration, withdrawing it is still a fleet-wide reconfiguration, and a leaked token is still a durable spam/forgery vector into `integration_health` for that one connection — bounded to that connection's own health row, never a credential Loxep authenticates outward with.

5. **OWNER-REVIEW-CRITICAL — Is "no mutating call to any fleet tool" a permanent rule?** This design says yes, and it is the rule most likely to be eroded by a reasonable-sounding request ("just a restart button for a container we can already see").

   *Recommendation:* make it permanent and testable — an adapter-level rule that only `GET` (plus the Gatus health push) may leave the fleet integration boundary, with a test per adapter rather than a code-review convention. The moment a restart button exists, Loxep is a container manager with a small feature set.

   *The owner must confirm:* that no lifecycle action ever appears in `/infrastructure`, and that the deep link is the permanent answer.

6. **Does `integration_health` ship as shared foundation, and does Phase 7 project into it?** Phase 6 and Phase 7 both assume the table; Phase 7 also carries private health columns.

   *Recommendation:* ship it in `@loxep/domain` as shared foundation, have Phase 7 write a projection alongside its own columns, and **never drop the owning tables' columns** — they drive retry and backoff, which this table must not. Reversible either way, which is why it is not marked critical, but shipping a fifth private copy of health state instead would make three documents false at once.

   *The owner must confirm:* the ownership call, and whether `hosting_target` and `managed_domain` belong in the subject set from the first migration or are added when Phase 7 lands.

7. **Does health history ever get stored?** This design stores current state only, deliberately.

   *Recommendation:* keep it that way. "How often was this host down last month" is Gatus's and Beszel's question and both answer it well; a Loxep history table is the first step toward the observation store this phase exists not to build. If it is ever wanted, it must arrive as an explicit ADR naming what Loxep can answer that the tools cannot.

   *The owner must confirm:* that a status timeline in `/infrastructure` is not expected.

8. **One metrics adapter, or none?** Beszel and Netdata occupy the same slot; Netdata has the better API and no credential model.

   *Recommendation:* at most one, ever, and Beszel if any — it is [already the recommended companion](../../product/companion-services/#infrastructure-operations), it is MIT, and it has a real credential to store. Netdata stays tier 2 plus an optional embed.

   *The owner must confirm:* which metrics tool the estate actually runs, since building the adapter for the other one is pure waste.

9. **RESOLVED 2026-08-15 (loxep-4ah, owner ruling 6b) — Does Loxep publish its own health into Gatus, and which facts?** The `external-endpoints` push is the cheapest new capability in the phase.

   *Recommendation:* yes, and first. It is the only mechanism here that solves the self-monitoring problem, it needs no new table, and its blast radius is one bearer token that can mark one Gatus endpoint healthy.

   *The owner confirmed:* both halves. "Yes, and first" shipped 2026-08-13 (milestone 2, loxep-ovj.2) — one push, one endpoint, no new table, the overall `integration_health` rollup. "Which facts" was answered 2026-08-15: widen it to the five-fact list this question named — worker backlog, order-sync freshness, notification delivery success, reconciler drift count, readiness — each published to its own Gatus `external-endpoints` entry, additive on top of the existing single-key shape via a new `mode: 'single' | 'facts'` setting field (PROVISIONAL default `'single'`, so every installation that has not opted in keeps EXACTLY the milestone 2 behavior). See the "OQ9 five-fact expansion" implementation-status paragraph above for what shipped, and the [gatus-health-push guide](../../guides/gatus-health-push/) for the operator-facing YAML.

10. **Do link-only tools stay out of the integrations catalog?** This design says yes: a catalog card implies an account and a credential.

    *The owner must confirm:* nothing security-relevant; flagged because it is the kind of detail that gets decided silently and wrongly, producing a `/settings/integrations` page full of bookmarks.

## Contradictions and tensions found in existing documentation

Recorded for a human to resolve; this document does not attempt to fix them.

1. **RESOLVED 2026-08-13 — Companion Services names Dockhand as the container-management companion, and this design originally gave it the weakest verdict of the six.** The conflict is gone: Dockhand is now tier 3 with a read surface and a host-registration intent surface, so the companion recommendation and this design agree. What a later reader still needs recorded next to that recommendation is the *shape* of the integration — Loxep reads Dockhand and reconciles its host inventory, and every container lifecycle action remains a deep link into Dockhand itself.

2. **The Master Domain Map's non-goal versus this phase's existence — again, and more sharply than Phase 7.** Phase 7 argued a narrow carve-out for DNS intent. Phase 8 has no equivalent argument to make and does not try: every capability here is either a link, a link plus a probe, or a read. That is the strongest form of the non-goal, not an exception to it. If the map's bullet is tightened as Phase 7 proposed, this phase is the evidence that the tightening is honest.

3. **`integration_health` is assumed by three documents and built by none.** Companion Services sketches it, Phase 6 states its integrations reuse it, Phase 7 lists the overlap with its own columns as an open tension. Whichever phase implements first must adopt the shape here or amend it; shipping a fourth private copy of health state would make all three documents false simultaneously.

4. **Phase 7 registers a scheduling target type; Phase 8 recommends a single sweep.** Both cite the same [shared scheduling rule](../domain-boundaries/#scheduling-is-shared-foundation-infrastructure) and reach different answers, for reasons stated in each. They should be reviewed together. If the shared model is chosen for both, Phase 8 becomes a fourth registering domain and the runtime registration seam Phase 7 raised is no longer optional.

5. **The notification foundation is described as transport-neutral and is only half so.** *(RESOLVED 2026-08-15, loxep-oii / ADR-0023: the ledger and the rule matcher are now subject-neutral — `notification_deliveries` is keyed on a `notification_events` row, and rules filter on an event class. The foundation document and the implementation agree again. The original observation is kept below as the record of why.)* [The foundational data model](../foundational-data-model/#notifications) presents notifications generically — endpoints, rules, deliveries — while the shipped `notification_deliveries` is keyed on `market_event_id NOT NULL`. The transport interface genuinely is neutral; the ledger and rule matcher are market-shaped. That is a reasonable Phase 1 decision and it is not what the foundation document says. Whether it is generalized or the document is corrected, the two should agree before a second domain tries to send a notification.

## Before implementing this phase

1. resolve open questions 1 through 5 — questions 1, 2, and 5 decide whether the phase's shape is correct at all, and questions 3 and 4 are unrecoverable once a credential is stored or a URL is distributed;
2. re-verify every upstream claim in the [per-tool verdicts](#per-tool-verdicts) against current sources. Netdata shipped 2026-08-12 and Dockhand 2026-08-09; Beszel is pre-1.0 and warns that its shapes change in minor releases. Nothing in that table should be trusted at implementation time because it appears here. **The 2026-08-13 re-verification proved the point twice over**: Beszel's verdict rested on a credential model that was simply wrong, and Dockhand's rested on a documentation contradiction that did not survive reading the reference. Both were argued confidently, and both were checkable in minutes;
3. confirm the Gatus auth-mode branch against a running instance before shipping a reader — the OIDC case cannot authenticate at all, and a reader that silently shows a partial status page is worse than one that refuses;
4. decide the `integration_health` ownership question (6) before the migration, since it determines the package and whether Phase 7 projects into it from day one;
5. write the sweep's idempotency tests before the sweep: two probes of the same subject, a subject deleted between probe and write, an unreachable subject rendering as unreachable rather than failing, and a stale `report` row deriving staleness from `checked_at`;
6. assert by test, per adapter, that no method other than `GET` can leave the fleet integration boundary — this is open question 5's rule made enforceable rather than aspirational;
7. assert by test that no fleet adapter writes a `notification_deliveries` row, so question 1's resolution cannot be eroded quietly;
8. confirm no probe or adapter can place a credential into `integration_health.detail`, a job payload, or a log line — a test per adapter, not a code review;
9. keep provider shapes at the integration boundary ([ADR-0009](../../decisions/0009-integration-boundaries/)); PocketBase record types and Gatus status structs must not become Loxep types;
10. update this document, the roadmap, Workspaces, and Domain Boundaries when implementation reality diverges, rather than letting the documentation drift.
