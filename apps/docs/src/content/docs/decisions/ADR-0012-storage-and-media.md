# ADR-0012 — Media and Object Storage

**Status:** Accepted

## Context

Loxep will need to retain user-provided and provider-derived files such as product images, receipts, invoices, installation photos, PDFs, contracts, shipping documents, exports, and other attachments.

The smallest self-hosted deployment should not require an object-storage service, while larger and distributed deployments must not be trapped by local filesystem storage.

## Decision

Loxep uses a storage-provider abstraction from the first implementation.

Supported initial storage drivers:

- `local` — filesystem-backed storage, intended as the zero-extra-service default;
- `s3` — generic S3-compatible object storage.

The database stores metadata and stable Loxep media identity. It does not store ordinary media/document blobs.

Loxep domain records reference `media_object.id`; they do not persist filesystem paths, S3 URLs, bucket URLs, or provider-specific object URLs as identity.

### Recommended S3 implementation

As of August 2026, Loxep documentation recommends **Garage** for small-to-medium self-hosted S3 deployments, especially where multi-node or multi-site resilience is desired.

Garage is a recommendation, not an application dependency. Loxep's contract is generic S3 compatibility.

Other supported/compatible choices may include:

- AWS S3 and compatible hosted services;
- Cloudflare R2 and similar S3-compatible services;
- SeaweedFS S3 gateway;
- RustFS when its distributed-production maturity meets the deployment's requirements;
- any sufficiently compatible S3 implementation validated by Loxep's storage conformance tests.

### Why Garage is the current recommendation

Garage explicitly targets small-to-medium self-hosted distributed object storage, including clusters whose nodes are in different physical locations and where some nodes may be unavailable. This maps well to Loxep's expected self-hosted audience.

### Why not RustFS as the default yet

RustFS is promising, Apache-2.0 licensed, and provides a familiar S3/MinIO-like operational model. Its current project documentation still marks distributed mode as under testing. Loxep should revisit this recommendation as RustFS matures.

### Why not SeaweedFS as the default

SeaweedFS is mature and highly capable, with S3, scalable volume servers, cross-cluster replication, tiering, FUSE/WebDAV, and other storage-system features. Those capabilities are valuable for advanced deployments but exceed what Loxep requires as its default object-store recommendation.

## Local-to-S3 migration is a product requirement

A user who starts with `local` must be able to migrate to `s3` without changing domain records.

The storage layer therefore requires a migration workflow with these semantics:

1. configure and test the destination storage backend;
2. copy each object by stable storage key while preserving metadata and checksum;
3. verify destination object length and checksum/hash where possible;
4. atomically update the media object's active backend/location only after verification;
5. leave the source intact until the migration is fully verified;
6. support resumable/idempotent migration jobs;
7. produce a migration report showing copied, verified, skipped, and failed objects;
8. optionally clean the source only through an explicit later action.

Loxep should eventually provide this as an administrative job/UI, not merely documentation for manually copying a directory.

## Logical media model

```text
media_objects
  id                  uuid
  storage_backend     text
  storage_key         text
  original_filename   text nullable
  mime_type           text nullable
  size_bytes          bigint
  sha256              text
  created_by_user_id  text nullable
  created_at           timestamptz
  metadata             jsonb

media_links
  media_object_id     uuid
  resource_type       text
  resource_id         uuid/text
  purpose             text
  sort_order          integer nullable
  created_at           timestamptz
```

`storage_key` is generated by Loxep and remains stable across storage providers where practical. A typical object may therefore migrate from:

```text
local:/data/media/ab/cd/<uuid>
```

to:

```text
s3://loxep-media/ab/cd/<uuid>
```

without changing the `media_object.id` referenced by the rest of the application.

## Distributed deployments

Workers do not require object storage to be co-located with them. Any web/worker node needs network access to the configured S3 endpoint.

A storage cluster may share physical servers with Loxep workers in small deployments, but Loxep does not assume that topology. Storage replication/failure domains and job-worker scaling are separate concerns.
