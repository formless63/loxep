---
title: "ADR-0012: Media and Object Storage"
---

**Status:** Accepted; self-hosted provider recommendation amended by ADR-0014; logical media model superseded by the `storage_backends` record design in the foundation schema draft.

## Context

Loxep will need to retain user-provided and provider-derived files such as product images, receipts, invoices, installation photos, PDFs, contracts, shipping documents, exports, and other attachments.

The smallest self-hosted deployment should not require an object-storage service, while larger and distributed deployments must not be trapped by local filesystem storage.

## Decision

Loxep uses a storage-provider abstraction from the first implementation.

Supported initial storage drivers:

- `local` — filesystem-backed storage, intended as the zero-extra-service default;
- `s3` — generic S3-compatible object storage.

The database stores metadata and stable Loxep media identity. It does not store ordinary media/document blobs.

Loxep domain records reference `media_object.id`; they do not persist filesystem paths, S3 URLs, bucket URLs, or provider-specific object URLs as identity.

### Initial self-hosted S3 recommendation

ADR-0014 selects **RustFS** as the initial recommended/tested self-hosted S3 companion for Loxep.

That recommendation does not change this ADR's architectural contract: Loxep integrates through generic S3 semantics and must remain portable to Garage, SeaweedFS S3, hosted S3-compatible services, and other sufficiently compatible implementations.

RustFS remains a separate service/container. Official Compose examples may include it as an optional profile so an operator can manage Loxep, PostgreSQL/TimescaleDB, and RustFS as one stack without combining unrelated processes into one image.

## Local-to-S3 migration is a product requirement

A user who starts with `local` must be able to migrate to `s3` without changing domain records.

The storage layer therefore requires a migration workflow with these semantics:

1. configure and test the destination storage backend;
2. copy each object by stable storage key while preserving metadata and checksum;
3. verify destination object length and checksum/hash where possible;
4. atomically update the media object's active backend/location only after verification;
5. leave the source intact until the migration is fully verified;
6. support resumable/idempotent migration jobs;
7. produce a migration report showing copied, verified, skipped, and failed objects;
8. optionally clean the source only through an explicit later action.

This should become an administrative application workflow, not merely documentation for manually copying a directory.

## Logical media model

> **Superseded:** this ADR's original sketch stored a bare `storage_backend text` driver name on each media object. The accepted foundation model instead represents each configured storage destination as a **`storage_backends` record** (driver family, config, secret reference), with `media_objects.storage_backend_id` as a foreign key and `unique(storage_backend_id, storage_key)`. This is what allows one installation to hold several configured destinations and migrate between them without changing media identity. The [Foundation Schema Draft](../architecture/foundation-schema/) is authoritative for the physical shape.

```text
storage_backends
  id, name, driver, enabled, is_default, config, secret reference, ...

media_objects
  id                  uuid
  storage_backend_id  uuid references storage_backends(id)
  storage_key         text
  original_filename   text nullable
  mime_type           text nullable
  size_bytes          bigint
  sha256              text
  created_by_user_id  text nullable
  created_at           timestamptz
  metadata             jsonb

media_links
  media_object_id     uuid
  resource_type       text
  resource_id         text
  purpose             text
  sort_order          integer nullable
  created_at           timestamptz
```

`storage_key` is generated by Loxep and remains stable across storage providers where practical. Storage migration changes the backend/location, not the `media_object.id` referenced by the rest of the application.

## Distributed deployments

Workers do not require object storage to be co-located with them. Any web/worker host needs network access to the configured S3 endpoint.

A storage node may share a physical server with a Loxep worker in small deployments, but Loxep does not assume that topology. Storage replication/failure domains and job-worker scaling are separate concerns.

Multi-host Loxep deployments should migrate away from node-local media unless the local path is genuinely shared storage.
